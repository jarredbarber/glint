Storage adapters

Glint reads and writes every backend through one StorageAdapter seam. This page covers the contract, the three shipped backends, and how to add your own.

Overview

An adapter maps Glint's document model onto a concrete store. The SPA never talks to a backend directly; it holds a single adapter instance and drives it through a small, backend-agnostic interface.

The adapter seam

Three identifiers travel with every file. Keeping them distinct is what lets navigation, rendering, and writes stay backend-native.

id, path, version

id is the backend read/write key, path is source-root-relative for navigation, and version is the concurrency token used on save.

Read and write keys

Adapters resolve id lazily so a folder listing stays cheap. Writes carry the last-seen version and surface a conflict rather than clobbering.

Backends

Three adapters ship today, each authenticating in its own native way.
