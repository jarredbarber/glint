# Issue Lifecycle

State machine and checkpoint protocol for GitHub Issues.

## States

```
                    ┌─────────────┐
                    │ needs-triage│
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌───────────┐ ┌──────────┐ ┌────────┐
        │ needs-info│ │ready-for-│ │ wontfix│
        └─────┬─────┘ │  agent   │ └────────┘
              │        └────┬─────┘
              │             │
              └──────┐      │ agent works
                     ▼      ▼
               ┌───────────────┐
               │ ready-for-    │◄──── agent can't verify
               │   agent       │      its own work
               └───────┬───────┘
                       │
          ┌────────────┼──── can verify ──── ✓ close
          │            │
          ▼            │
   ┌──────────────┐    │
   │ ready-for-   │    │
   │   human      │    │
   └──────┬───────┘    │
          │            │
    human reviews      │
          │            │
    ┌─────┼─────┐      │
    ▼     ▼     ▼      │
 approve revise reject │
    │     │     │      │
    │     │     ▼      │
    │     │   close    │
    │     │            │
    └─────┴────────────┘
       ready-for-agent
```

## Escalation rule

An agent moves an issue to `ready-for-human` **only** when it cannot verify its own work:

1. **UI changes** — no way to see the rendered result
2. **Auth/credential-gated** — can't access the service to test
3. **Subjective** — no objective acceptance criteria
4. **Product-level** — direction, priorities, scope decisions

Everything else: complete the work, verify it, close the issue.

Both the triaging agent and the implementing agent can escalate. The bar is "I cannot verify this," not "the maintainer might have a preference."

## Checkpoint brief

When moving an issue to `ready-for-human`, post a comment with the session link and a self-contained summary. The reader should never need to open another file to understand what was done or make a decision.

```markdown
> *This was generated by AI during triage.*

## Checkpoint

**Session:** <claude session link for follow-up questions>

**Summary:** one-line description of what was done

### Design

<Self-contained description of the design/work. Structured as:>

**Problem:** what this solves

**Solution:** what was built or proposed, described behaviorally (not file paths)

**Key decisions:**
- Chose X over Y because Z
- Deferred W (upgrade path: ...)

**Out of scope:** what was explicitly excluded

**Risks:** what could go wrong with this approach

### Follow-up work

<If the checkpoint proposes follow-up tasks, describe them as vertical slices
with blocking edges. Each slice should be demoable/verifiable on its own and
sized for a single agent context window.>

1. **Slice title** — what it delivers end-to-end. Blocked by: none / #N.
2. **Slice title** — what it delivers. Blocked by: #1.

---

**To approve:** comment "approved" (or move to ready-for-agent)
**To revise:** comment with feedback (move to ready-for-agent)
**To reject:** close the issue
```

Not every section is required. A simple UI checkpoint might only need Summary + a screenshot description + the decision footer. A design checkpoint needs the full Design section. Use judgment — include what the reviewer needs, skip what they don't.

Design artifacts live in the issue comment, not in repo files. The issue is the canonical record; when it closes, the design is archived with its decision history.

## Human response

The human reads the checkpoint brief and does one of:

| Action | What to do | What happens next |
|--------|-----------|-------------------|
| **Approve** | Comment "approved" and/or relabel `ready-for-agent` | Agent picks up and executes the proposal |
| **Revise** | Comment with specific feedback, relabel `ready-for-agent` | Agent reworks based on feedback |
| **Reject** | Close the issue | Done |

The agent reads the latest comment to understand which response was given. No extra labels needed.

## Agent brief (for `ready-for-agent`)

When an issue moves to `ready-for-agent` (whether from triage or from human approval), an agent brief should be attached. See the triage skill's `AGENT-BRIEF.md` for the template and principles.
